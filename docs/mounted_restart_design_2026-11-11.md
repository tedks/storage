# Mounted maintenance and restart: bounded design investigation

**Status:** design proposal, 2026-11-11; product rulings accepted 2026-11-17 (see [Product rulings](#product-rulings-2026-11-17)). **Source snapshot:** `66c640aec005feccd0bd585f3355295c3bb772ba`; every line-anchored source link below is pinned to that commit, so the cited lines are the evidence the analysis used. The one exception is the "Since the snapshot" note, which cites master `0953369` and says so. This document authorizes no runtime feature, live operation, mount change or rollout. As of the snapshot, PR 171's responsiveness contracts were proposals (still open and unaccepted on 2026-11-17), and PR 170's gate incident was unresolved; neither is an implementation premise here.

## Assumptions and intended result

- “Mounted” means the same kernel FUSE connection stays attached at the mountpoint. “Open-handle continuity” additionally means an already open file descriptor keeps its file identity and can still receive valid reads, writes, `fsync`, and `release` after maintenance. These are distinct promises.
- The first target is an operator-initiated, in-process maintenance step for **one SSH member transport and its SFTP and exec channels**. The FUSE frontend, cache, SQLite index, mount lock, member identity, sync policy, and application file handles stay in the same daemon. This is a proposal, not an existing command.
- New work for the member waits for a bounded interval during maintenance, and a drain that misses its deadline leaves the active transfer running and reports maintenance incomplete (ruled 2026-11-17; this supersedes the original draft's open choice between a bounded wait and a prompt refusal). Zero latency, uninterrupted remote reads, and transparent retry of non-idempotent remote writes are not assumed.
- The actual implementation must be proven with synthetic FUSE tests on isolated temporary storage before any live mount is considered. No such test or live operation was run for this investigation.

## Product rulings (2026-11-17)

Ted ruled on the two open product questions on 2026-11-17, recorded when ditz `oq-mounted-daemon-handoff-scope` and `oq-mounted-sftp-maintenance-semantics` were closed on the `ditz-metadata` branch. The ruling text, verbatim from those closures:

> Target one member connection in the same daemon, preserving the mount and open handles. Whole-daemon replacement requires a separate feasibility study.
>
> New requests wait for a bounded interval. If an active transfer exceeds the drain deadline, leave it running and report that maintenance did not complete.

The CTO accepted them for this proposal. Each numbered item below states a ruling and then this design's reading of it; the reading is open to review, the ruling is not. They supersede the original draft's "wait or refuse" alternatives for new work, its "refuses within the deadline" and "not restarted" outcome for a drain that times out, and the open P0 question; the sections below are updated to match, and "refused" now means only that maintenance could not start.

1. **Same daemon, one member connection.** Maintenance targets one SSH member connection inside the running daemon, preserving the mount and open handles. Whole-daemon replacement is out of this target and needs a separate feasibility study first (P4 below) before anything about it is promised.
2. **Bounded wait for new work.** A new SFTP lease or exec channel for the member that arrives while the connection drains waits, for a bounded interval, instead of failing promptly. It proceeds on whichever transport is admitted when the wait ends: the new, already connected one after a completed recycle, or the unchanged old one after an incomplete one. After a failed recycle (old transport retired, new connect failed) it sees the member's ordinary unavailability and reconnect behaviour, as after any outage. The wait is bounded by the drain deadline plus a reconnect allowance that P1 chooses and enforces with its own deadline. The member's existing connect timeout does not bound a whole connect: it is applied separately to the TCP connect, banner and authentication phases, paramiko's name lookup before them has no timeout, and a lookup failure adds a host-resolver fallback and a second connect ([`ssh.py` 205–250](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/backends/ssh.py#L205-L250)). So a waiter still waiting when the allowance expires gets today's `MemberUnavailable`, whatever the connect thread is still doing, and the maintenance outcome is failed; a connect that finishes later may still install its transport, as an ordinary reconnect would. Separately, the request's own existing deadlines (interactive connect wait, opt-in bulk capacity deadline, native-request cancellation) still apply. When one of those fires, the request gets the error it gets today, not a new maintenance-specific one.
3. **Drain timeout keeps the transfer.** If an active transfer (streaming range, sync upload, `release` upload in direct mode, or exec command) still holds the connection at the drain deadline, it keeps running on the old transport, maintenance reopens admission to that transport, and the outcome is reported as **incomplete**. A recycle needs a connected transport to start from: if the member has none, or a connection attempt is still installing one, maintenance is **refused** and that attempt continues under ordinary reconnect policy. If the old transport fails for real during the drain, its users get today's errors and maintenance goes on to connect the new transport, reporting completed or failed. The planned transition never closes an active channel to meet its deadline.

What the rulings leave to P1 and P2: the numeric deadline and its default, the outcome record's exact fields, and how the operator sees the result. Those are implementation and interface choices for review, not further product questions.

**Since the snapshot.** Master gained an opt-in capacity deadline for bulk SFTP leases (`BulkCapacityTimeout`) and cancellation of a queued bulk lease when its native FUSE request ends (`BulkCapacityCancelled`) ([`ssh_pool.py` at 0953369, `MemberConnection._acquire_new_sftp`](https://github.com/tedks/storage/blob/0953369de47a7e9b46a0edca8facfee99d6bb490/storage/backends/ssh_pool.py#L826-L867)). A drain admission gate placed in that acquisition path would hold new leases inside the same loop, so P1 must keep both checks live during the drain wait (ruling 2) instead of adding a wait that ignores them. This changes no conclusion above.

## What the current process owns

The mount CLI constructs members ([`cli_mount.py` 231–249](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/cli_mount.py#L231-L249)) and passes them to [`mount_storage`](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/cli_mount.py#L311-L335), which acquires a cache/mountpoint lock, creates one `StorageFS`, and enters `FUSE(fs, ...)` ([`fs.py` 3322–3359](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/fs.py#L3322-L3359)). Bazel uses a pip lock that pins fusepy 3.0.1 ([`requirements.lock`](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/requirements.lock#L19), [`MODULE.bazel` 19–26](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/MODULE.bazel#L19-L26)). The Nix-packaged CLI instead declares `python.pkgs.fusepy`, whose version this investigation did not inspect ([`flake.nix` 44–72](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/flake.nix#L44-L72)). The mount loads libfuse 2 (host copy or Nix fallback; [`flake.nix` 15–41](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/flake.nix#L15-L41)). fusepy 3.0.1's `FUSE` constructor calls `fuse_main_real` synchronously and maps the kernel's `fh` to the value returned by `StorageFS.open` ([fusepy 3.0.1 source, `FUSE.__init__`, `open`, `read`, `write`](https://sources.debian.org/src/python-fusepy/3.0.1-5/fuse.py/)). It exposes no supported callback-table or live-session handoff in that interface; an implementation phase must verify the Nix package's corresponding behavior.

`StorageFS.open/create` gives the kernel a process-local virtual handle and stores its raw cache fd, path, flags, and optional prefetch session in `_fd_map` ([`fs.py` 2265–2353](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/fs.py#L2265-L2353), [2360–2406](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/fs.py#L2360-L2406)). `read`, `write`, `release`, and `fsync` resolve that map ([2411–2469](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/fs.py#L2411-L2469), [2476–2569](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/fs.py#L2476-L2569)). A new Python process cannot infer this table from the SQLite index. A streaming reader also holds a live `PrefetchSession`, partial cache file, worker, and fd; `destroy()` explicitly detaches or waits for these sessions ([`streaming.py` 229–273](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/streaming.py#L229-L273)).

On unmount, libfuse finishes the request loop before `StorageFS.destroy` (the ordering assumed in [`fs.py` 3269–3277](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/fs.py#L3269-L3277) and [`namespace.py` 1026–1038](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/namespace.py#L1026-L1038)). `destroy` then stops streaming and watchers, cancels checksum/listing work, stops sync workers, closes shared SSH sockets and member transports, closes the index, and releases the lock ([`fs.py` 2936–2990](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/fs.py#L2936-L2990)). The cleanup is intentionally best effort and has bounded joins; it is **not** a reversible in-place pause. In particular, namespace shutdown permanently marks its listing executors shut down ([`namespace.py` 1016–1052](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/namespace.py#L1016-L1052)), and SSH `close()` permanently disables reconnect ([`ssh_pool.py` 506–519](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/backends/ssh_pool.py#L506-L519)). Calling `destroy` while mounted would close facilities that incoming FUSE requests still use.

The kernel documentation defines a FUSE connection as lasting until its daemon dies or the filesystem is unmounted, and says abort makes pending and future requests fail ([Linux FUSE overview, definitions and control filesystem](https://www.kernel.org/doc/html/latest/filesystems/fuse/fuse.html#definitions), [abort section](https://www.kernel.org/doc/html/latest/filesystems/fuse/fuse.html#aborting-a-filesystem-connection)). A process `exec` also discards the Python objects and raw fd map. Passing `/dev/fuse` to a replacement and reconstructing libfuse's high-level state might be a research project, but this repository's fusepy interface and current process-local handles provide no supported handoff. **Replacing the daemon with no mount or open-handle interruption cannot be promised.** A new mount at the same path after unmount is a new connection and does not preserve existing descriptors.

## Safety contract for an in-process maintenance step

1. **Frontend lifetime.** Never call `FUSE` teardown, `StorageFS.destroy`, `NamespaceService.shutdown`, `StateManager.close`, or release the mount lock during a member maintenance transition. Existing `_fd_map` entries retain their identity and raw cache fd. The frontend continues dispatching unrelated paths.
2. **Write authority.** Every acknowledged canonical write remains represented by the cache bytes and its dirty generation; a sync result may publish only for the generation it read ([`fs.py` 2444–2471](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/fs.py#L2444-L2471), [`cache.py` 411–434](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/cache.py#L411-L434), [`state.py` 285–312](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/state.py#L285-L312), [354–378](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/state.py#L354-L378)). A planned transition cannot turn DIRTY into CLEAN, discard a queued task, or let a prior worker publish a stale status. `fsync` syncs the cache fd, while `release` calls a cache flush that currently suppresses `OSError`; therefore the design must not describe remote replication or every close as durably complete ([`fs.py` 2522–2549, 2554–2569](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/fs.py#L2522-L2549), [`cache.py` 550–559](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/cache.py#L550-L559)).
3. **No severing an active user.** A planned transport recycle must wait, up to its drain deadline, while any request owns an SFTP lease **or exec channel**, and it does not start while a connection attempt is still installing a transport (ruling 3). Streaming range fetches, foreground metadata calls, background listing/hash tasks, sync, and a direct-mode `release` (which uploads synchronously; [`fs.py` 2522–2549](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/fs.py#L2522-L2549)) can all be users. Nested SFTP acquisition by a thread already holding a lease must be allowed to complete during drain ([`ssh_pool.py` 777–804](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/backends/ssh_pool.py#L777-L804), [963–982](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/backends/ssh_pool.py#L963-L982)). No forced close of their channel is a “clean” restart. At the deadline the active work keeps running on the old transport and the result is **incomplete** (ruling 3); it does not silently switch to `mark_down()`.
4. **No invisible watcher gap.** If a phase stops a remote watcher, it must invalidate affected listing snapshots and remembered member stats before resuming reads. A fully watchable mount gives listings an infinite TTL; missed events otherwise persist ([`fs.py` 267–281, 660–716](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/fs.py#L267-L281)). Current watcher resync calls `NamespaceService.invalidate_all_listings`, which clears its listing/stat memo but does not itself clear `StorageFS._member_checks`; a separate watcher phase must check that cached-file revalidation cannot be postponed by a recent member check ([`namespace.py` 316–334](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/namespace.py#L316-L334), [`fs.py` 1650–1655](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/fs.py#L1650-L1655)). A pool recycle does not claim to restart the separate SSH/inotify watcher or rsync master sockets.
5. **Bounded and observable.** Maintenance has one active owner and a finite deadline, an outcome of **completed** (old transport retired and a new one connected and admitted before the outcome is reported), **incomplete** (the drain did not finish: its deadline passed with work still active, or the maintenance request itself was cancelled before retirement; the outcome names which), **refused** (could not start: another maintenance already owns the member, the member is not an SSH member, or it has no connected transport to recycle), or **failed** (old transport retired, and the new connect failed or did not finish within the reconnect allowance), with the affected member and generation, and a safe unwind that reopens admission if no swap occurred. If old work has not drained, keep the old transport. The old transport is retired only after the drain, so a new connect that fails cannot fall back to it: report failed and leave the member to existing unavailability and reconnect semantics. Report completed only after the new transport is seen connected; a queued command or a retirement alone is not completion. Cancelling the maintenance request is distinct from a waiting request's own cancellation (for example its native FUSE request ending): the latter ends only that request, with the error it gets today, and does not change the maintenance outcome.

These invariants do not imply no perceptible pause: requests for the targeted member can wait, fail due to a real outage, or need a caller retry. The safe promise is that a planned transition will not deliberately kill an active lease, lose a recorded dirty write, or close the FUSE session.

## Options and consequences

| Option | Mount and open handles | Request interruption | Write durability and limit |
|---|---|---|---|
| Let the existing SSH pool recover an actual failure | Same FUSE process and `_fd_map` | A failed channel may return an error; retry is only enabled on selected repeatable operations ([`ssh.py` 270–300](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/backends/ssh.py#L270-L300)) | Dirty cache and generation rules remain; this is failure recovery, not a planned clean recycle. |
| **Recommended first implementation:** quiescent recycle of one SSH member transport in the live daemon | Same FUSE session and local file handles | New SFTP and exec channels wait for a bounded interval (ruling 2); active channels finish, or keep running past the deadline with an incomplete result (ruling 3); unrelated members continue | No cache/index or sync-policy change. A sync using the member must finish before the old pool is retired. It does not restart watcher, rsync, or daemon. |
| Pause/rebuild background workers or reconfigure member set in place | Frontend may stay, but only after an explicit lifecycle protocol | Larger pause and more race surfaces; existing `stop()` joins for 5 seconds then clears workers, so an old worker can outlive the stop and race a restart ([`sync.py` 226–253](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/sync.py#L226-L253)) | Requires fencing old workers, queued-task reconciliation, generation checks, watcher resync, and a policy for open streams/handles. Not yet safe as a command. |
| Stop/`exec`/replace the whole daemon | No supported preservation in current fusepy/high-level libfuse path | Connection may abort or unmount; existing handles cannot be rebound from persisted state | Requires a new session/handle-transfer architecture and kernel/libfuse proof. No no-downtime promise. |
| Conventional clean unmount and remount | New mount and connection; old handles are not preserved | Full interval without service; callers must close/reopen | Existing unclean-shutdown sweep and mount lock are designed around this lifecycle ([`fs.py` 3038–3075](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/fs.py#L3038-L3075)). Use as operational fallback, not “mounted restart.” |

`MemberConnection.mark_down()` drops the transport and increments its generation immediately, including channels held by current requests; `clear_down()` merely allows the next lease to reconnect ([`ssh_pool.py` 479–504](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/backends/ssh_pool.py#L479-L504)). `close()` is final ([506–519](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/backends/ssh_pool.py#L506-L519)). The connection also hosts exec channels ([963–1015](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/backends/ssh_pool.py#L963-L1015)). A new planned recycle therefore needs a small **admission/drain/reconnect** operation across both channel types at that pool boundary, not a call to either existing method masquerading as graceful maintenance. The pool's watchdog bounds a stalled SSH channel request by closing it; deadline callbacks and their own threads are a failure mechanism, not a request-draining barrier ([`ssh_pool.py` 154–299](https://github.com/tedks/storage/blob/66c640aec005feccd0bd585f3355295c3bb772ba/storage/backends/ssh_pool.py#L154-L299)).

**Necessity challenge:** P1 adds only the missing drain boundary to an already reconnecting pool. Without it, the only existing “reset” closes active channels and violates the proposed clean-maintenance contract. P2–P4 are conditional; a supervisor, whole-daemon rewrite, and generic reconfiguration framework have no demonstrated necessity for the first target.

## Synthetic acceptance plan and rollback

All test data, mountpoints, caches, members, and processes must be isolated fixtures. The proposed P1 gate should inject a deterministic barrier inside an SFTP lease, request recycle, then issue a second lease. Check that the old request completes unchanged, the second waits no longer than the ruled bound and then runs on the admitted transport, the transition either completes once or, with the first lease still held at the deadline, returns incomplete while that lease keeps running, and the next request uses the intended pool generation. Repeat with a nested lease, a thread holding an SFTP lease that then asks for an exec channel on the same member (and the reverse; none was found at the snapshot, but without a cross-kind exemption it would wait on the drain until incomplete), an active exec channel, a direct-mode `release` upload, a connection attempt in progress at start (refused), the old transport failing mid-drain, a stalled watchdog request, a stream range fetch, a sync upload overlapping a local write, a queued sync retry, cancellation before and after drain, a failed reconnect, and a reconnect stalled in name resolution or the SSH banner (waiters released at the allowance, outcome failed). Assert the dirty generation and cache bytes survive; a stale worker cannot publish CLEAN. Run both FUSE loop modes for mounted integration once implementation exists, then the repository's full local and remote gates on the exact commit ([`AGENTS.md`, build and test](../AGENTS.md#build-and-test)). This is a test **plan**, not executed evidence.

P1 rollback is local: on the drain deadline or cancellation before retirement, reopen admission to the unchanged old transport and report incomplete; once retirement has happened there is no old transport to restore: report completed if the new connect succeeded and failed if it did not, and let ordinary reconnect policy act. Do not roll back dirty generations or replay an unknown remote mutation. A test showing an active lease closed by planned recycle, a lost DIRTY row, an unbounded blocked request, stale CLEAN after an overlapping write, or missed watcher invalidation stops the phase. A live daemon or mount failure exits this proposal's authority; it requires a separately approved operational response.

## Primary external references and limits

- [Linux kernel FUSE overview](https://www.kernel.org/doc/html/latest/filesystems/fuse/fuse.html): connection lifetime, `/dev/fuse` fd, request/abort behavior. Its statement about daemon death supports the conservative no-handoff conclusion; it does not prove that every conceivable custom handoff is impossible.
- [fusepy 3.0.1 source](https://sources.debian.org/src/python-fusepy/3.0.1-5/fuse.py/): `FUSE.__init__` calls `fuse_main_real`; `open/read/write/release` use high-level `fh` callbacks. This is the version pinned for Bazel/pip, as packaged by Debian; no live handoff interface is visible in that binding. The Nix-packaged CLI's version remains to be verified before implementation.
- [libfuse API documentation](https://libfuse.github.io/doxygen/fuse__lowlevel_8h.html): low-level session APIs are a different integration surface. Their existence is not evidence that this fusepy 3.0.1/high-level mount can transfer a live session safely.

Source analysis only: no active mount, cache, backing member, host, daemon, Docker, benchmark, or test was touched.
