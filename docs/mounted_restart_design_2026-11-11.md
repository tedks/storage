# Mounted maintenance and restart: bounded design investigation

**Status:** design proposal for review, 2026-11-11. **Source snapshot:** `66c640aec005feccd0bd585f3355295c3bb772ba`. This document authorizes no live operation or rollout. PR 171's responsiveness contracts are proposals, and PR 170's gate incident remains unresolved; neither is an implementation premise here.

## Assumptions and intended result

- “Mounted” means the same kernel FUSE connection stays attached at the mountpoint. “Open-handle continuity” additionally means an already open file descriptor keeps its file identity and can still receive valid reads, writes, `fsync`, and `release` after maintenance. These are distinct promises.
- The first target is an operator-initiated, in-process maintenance step for **one SSH member transport and its SFTP and exec channels**. The FUSE frontend, cache, SQLite index, mount lock, member identity, sync policy, and application file handles stay in the same daemon. This is a proposal, not an existing command.
- A bounded wait or a reported refusal is acceptable in a proposed first phase. Zero latency, uninterrupted remote reads, and transparent retry of non-idempotent remote writes are not assumed.
- The actual implementation must be proven with synthetic FUSE tests on isolated temporary storage before any live mount is considered. No such test or live operation was run for this investigation.

## What the current process owns

The mount CLI constructs members and passes them to [`mount_storage`](../storage/cli_mount.py#L231-L249), which acquires a cache/mountpoint lock, creates one `StorageFS`, and enters `FUSE(fs, ...)` ([`fs.py` 3322–3359](../storage/fs.py#L3322-L3359)). Bazel uses a pip lock that pins fusepy 3.0.1 ([`requirements.lock`](../requirements.lock#L19), [`MODULE.bazel` 19–26](../MODULE.bazel#L19-L26)). The Nix-packaged CLI instead declares `python.pkgs.fusepy`, whose version this investigation did not inspect ([`flake.nix` 44–72](../flake.nix#L44-L72)). The mount loads libfuse 2 (host copy or Nix fallback; [`flake.nix` 15–41](../flake.nix#L15-L41)). fusepy 3.0.1's `FUSE` constructor calls `fuse_main_real` synchronously and maps the kernel's `fh` to the value returned by `StorageFS.open` ([fusepy 3.0.1 source, `FUSE.__init__`, `open`, `read`, `write`](https://sources.debian.org/src/python-fusepy/3.0.1-5/fuse.py/)). It exposes no supported callback-table or live-session handoff in that interface; an implementation phase must verify the Nix package's corresponding behavior.

`StorageFS.open/create` gives the kernel a process-local virtual handle and stores its raw cache fd, path, flags, and optional prefetch session in `_fd_map` ([`fs.py` 2265–2353](../storage/fs.py#L2265-L2353), [2360–2406](../storage/fs.py#L2360-L2406)). `read`, `write`, `release`, and `fsync` resolve that map ([2411–2469](../storage/fs.py#L2411-L2469), [2476–2569](../storage/fs.py#L2476-L2569)). A new Python process cannot infer this table from the SQLite index. A streaming reader also holds a live `PrefetchSession`, partial cache file, worker, and fd; `destroy()` explicitly detaches or waits for these sessions ([`streaming.py` 229–273](../storage/streaming.py#L229-L273)).

On unmount, libfuse finishes the request loop before `StorageFS.destroy` (the ordering assumed in [`fs.py` 3269–3277](../storage/fs.py#L3269-L3277) and [`namespace.py` 1026–1038](../storage/namespace.py#L1026-L1038)). `destroy` then stops streaming and watchers, cancels checksum/listing work, stops sync workers, closes shared SSH sockets and member transports, closes the index, and releases the lock ([`fs.py` 2936–2990](../storage/fs.py#L2936-L2990)). The cleanup is intentionally best effort and has bounded joins; it is **not** a reversible in-place pause. In particular, namespace shutdown permanently marks its listing executors shut down ([`namespace.py` 1016–1052](../storage/namespace.py#L1016-L1052)), and SSH `close()` permanently disables reconnect ([`ssh_pool.py` 506–519](../storage/backends/ssh_pool.py#L506-L519)). Calling `destroy` while mounted would close facilities that incoming FUSE requests still use.

The kernel documentation defines a FUSE connection as lasting until its daemon dies or the filesystem is unmounted, and says abort makes pending and future requests fail ([Linux FUSE overview, definitions and control filesystem](https://www.kernel.org/doc/html/latest/filesystems/fuse/fuse.html#definitions), [abort section](https://www.kernel.org/doc/html/latest/filesystems/fuse/fuse.html#aborting-a-filesystem-connection)). A process `exec` also discards the Python objects and raw fd map. Passing `/dev/fuse` to a replacement and reconstructing libfuse's high-level state might be a research project, but this repository's fusepy interface and current process-local handles provide no supported handoff. **Replacing the daemon with no mount or open-handle interruption cannot be promised.** A new mount at the same path after unmount is a new connection and does not preserve existing descriptors.

## Safety contract for an in-process maintenance step

1. **Frontend lifetime.** Never call `FUSE` teardown, `StorageFS.destroy`, `NamespaceService.shutdown`, `StateManager.close`, or release the mount lock during a member maintenance transition. Existing `_fd_map` entries retain their identity and raw cache fd. The frontend continues dispatching unrelated paths.
2. **Write authority.** Every acknowledged canonical write remains represented by the cache bytes and its dirty generation; a sync result may publish only for the generation it read ([`fs.py` 2444–2471](../storage/fs.py#L2444-L2471), [`cache.py` 411–434](../storage/cache.py#L411-L434), [`state.py` 285–312, 354–378](../storage/state.py#L285-L312)). A planned transition cannot turn DIRTY into CLEAN, discard a queued task, or let a prior worker publish a stale status. `fsync` syncs the cache fd, while `release` calls a cache flush that currently suppresses `OSError`; therefore the design must not describe remote replication or every close as durably complete ([`fs.py` 2522–2549, 2554–2569](../storage/fs.py#L2522-L2549), [`cache.py` 550–559](../storage/cache.py#L550-L559)).
3. **No severing an active user.** A planned transport recycle must refuse or wait while any request owns an SFTP lease **or exec channel**, or a connection attempt is still installing a transport. Streaming range fetches, foreground metadata calls, background listing/hash tasks, and sync can all be users. Nested SFTP acquisition by a thread already holding a lease must be allowed to complete during drain ([`ssh_pool.py` 777–804, 963–982](../storage/backends/ssh_pool.py#L777-L804)). No forced close of their channel is a “clean” restart. A deadline returns **not restarted**; it does not silently switch to `mark_down()`.
4. **No invisible watcher gap.** If a phase stops a remote watcher, it must invalidate affected listing snapshots and remembered member stats before resuming reads. A fully watchable mount gives listings an infinite TTL; missed events otherwise persist ([`fs.py` 267–281, 660–716](../storage/fs.py#L267-L281)). Current watcher resync calls `NamespaceService.invalidate_all_listings`, which clears its listing/stat memo but does not itself clear `StorageFS._member_checks`; a separate watcher phase must check that cached-file revalidation cannot be postponed by a recent member check ([`namespace.py` 316–334](../storage/namespace.py#L316-L334), [`fs.py` 1650–1655](../storage/fs.py#L1650-L1655)). A pool recycle does not claim to restart the separate SSH/inotify watcher or rsync master sockets.
5. **Bounded and observable.** Maintenance has one active owner and a finite deadline, an outcome of completed/refused/failed with the affected member and generation, and a safe unwind that reopens admission if no swap occurred. If old work has not drained, keep the old transport; if a new transport fails, restore admission to the old usable one or report member unavailability through existing semantics. Never report completion from a queued command alone.

These invariants do not imply no perceptible pause: requests for the targeted member can wait, fail due to a real outage, or need a caller retry. The safe promise is that a planned transition will not deliberately kill an active lease, lose a recorded dirty write, or close the FUSE session.

## Options and consequences

| Option | Mount and open handles | Request interruption | Write durability and limit |
|---|---|---|---|
| Let the existing SSH pool recover an actual failure | Same FUSE process and `_fd_map` | A failed channel may return an error; retry is only enabled on selected repeatable operations ([`ssh.py` 270–300](../storage/backends/ssh.py#L270-L300)) | Dirty cache and generation rules remain; this is failure recovery, not a planned clean recycle. |
| **Recommended first implementation:** quiescent recycle of one SSH member transport in the live daemon | Same FUSE session and local file handles | New SFTP and exec channels wait or refuse within a bound; active channels finish; unrelated members continue | No cache/index or sync-policy change. A sync using the member must finish before the old pool is retired. It does not restart watcher, rsync, or daemon. |
| Pause/rebuild background workers or reconfigure member set in place | Frontend may stay, but only after an explicit lifecycle protocol | Larger pause and more race surfaces; existing `stop()` joins for 5 seconds then clears workers, so an old worker can outlive the stop and race a restart ([`sync.py` 226–253](../storage/sync.py#L226-L253)) | Requires fencing old workers, queued-task reconciliation, generation checks, watcher resync, and a policy for open streams/handles. Not yet safe as a command. |
| Stop/`exec`/replace the whole daemon | No supported preservation in current fusepy/high-level libfuse path | Connection may abort or unmount; existing handles cannot be rebound from persisted state | Requires a new session/handle-transfer architecture and kernel/libfuse proof. No no-downtime promise. |
| Conventional clean unmount and remount | New mount and connection; old handles are not preserved | Full interval without service; callers must close/reopen | Existing unclean-shutdown sweep and mount lock are designed around this lifecycle ([`fs.py` 3038–3075](../storage/fs.py#L3038-L3075)). Use as operational fallback, not “mounted restart.” |

`MemberConnection.mark_down()` drops the transport and increments its generation immediately, including channels held by current requests; `clear_down()` merely allows the next lease to reconnect ([`ssh_pool.py` 479–504](../storage/backends/ssh_pool.py#L479-L504)). `close()` is final ([506–519](../storage/backends/ssh_pool.py#L506-L519)). The connection also hosts exec channels ([963–1015](../storage/backends/ssh_pool.py#L963-L1015)). A new planned recycle therefore needs a small **admission/drain/reconnect** operation across both channel types at that pool boundary, not a call to either existing method masquerading as graceful maintenance. The pool's watchdog bounds a stalled SSH channel request by closing it; deadline callbacks and their own threads are a failure mechanism, not a request-draining barrier ([`ssh_pool.py` 154–299](../storage/backends/ssh_pool.py#L154-L299)).

## Staged work packages (proposed, not claimed or READY)

| Package | Owned boundary and acceptance evidence | Stop condition |
|---|---|---|
| **P0: settle operator contract** (`oq-mounted-sftp-maintenance-semantics`) | Decide whether new operations targeting the member wait up to a deadline or fail promptly, and whether a user-visible failed maintenance request is acceptable when a long stream or sync holds a lease. Document precise error and outcome semantics. This is a product ruling. | No implementation of a control command until ruled. |
| **P1: one-member SSH pool drain/recycle** (`mounted-sftp-pool-recycle`) | Add an internal pool operation: stop admitting new SFTP and exec channels for the selected member, let a current owner's nested lease complete, wait for all active channels/connection attempts to finish, retire idle channels, reconnect or allow the next lease to reconnect, reopen admission. Preserve the existing pool on timeout. Synthetic tests cover simultaneous foreground read, sync upload, delayed/hung SFTP and exec calls, new leases, cancellation, and failure; assert no active channel closed by a planned transition and no duplicate non-idempotent write. Expose only a testable internal API first. | A channel or connection attempt cannot be counted/fenced reliably; no bounded unwind; any cache/index or FUSE lifecycle change appears necessary. |
| **P2: operator interface and independent watchers** | After P1 evidence and ruling, offer a narrow command for one transport, with explicit completed/refused/failed result and status. If watcher/rsync recycling is needed, design separate scope and tests for event gaps, shared sockets, and cache invalidation; do not roll it into P1 implicitly. | Any need to stop a watcher without a proven resync/invalidation barrier. |
| **P3: worker/reconfiguration investigation** (`mounted-worker-reconfig-contract`) | Separately define reversible sync-worker pause and member-set changes. Prove all old workers are gone before restart, queue dedup and directory operations survive, dirty generations remain authoritative, listing/hash futures are fenced, streams pinned to removed members settle, and existing handles retain meaning. Review proposed PR 171 contracts only after acceptance and against their then-current head. | A 5-second join leaves a live worker, in-flight data or policy cannot be reconciled, or a member identity changes under an open handle. |
| **P4: daemon handoff research, only if required** (`oq-mounted-daemon-handoff-scope`) | A distinct kernel/libfuse/fusepy feasibility study with a tiny synthetic prototype, including `/dev/fuse` ownership, FUSE request and handle state, callbacks, crash recovery, and rollback. No deployment promise or implementation package follows automatically. | No documented, reproducible same-connection handoff; stop and retain the in-process scope. |

**Necessity challenge:** P1 adds only the missing drain boundary to an already reconnecting pool. Without it, the only existing “reset” closes active channels and violates the proposed clean-maintenance contract. P2–P4 are conditional; a supervisor, whole-daemon rewrite, and generic reconfiguration framework have no demonstrated necessity for the first target.

## Synthetic acceptance plan and rollback

All test data, mountpoints, caches, members, and processes must be isolated fixtures. The proposed P1 gate should inject a deterministic barrier inside an SFTP lease, request recycle, then issue a second lease. Check that the old request completes unchanged, the second waits or receives the ruled error, the transition either completes once or refuses within the deadline, and the next request uses the intended pool generation. Repeat with a nested lease, an active exec channel, a connection attempt, a stalled watchdog request, a stream range fetch, a sync upload overlapping a local write, a queued sync retry, cancellation before and after drain, and a failed reconnect. Assert the dirty generation and cache bytes survive; a stale worker cannot publish CLEAN. Run both FUSE loop modes for mounted integration once implementation exists, then the repository's full local and remote gates on the exact commit ([`AGENTS.md`, build and test](../AGENTS.md#build-and-test)). This is a test **plan**, not executed evidence.

P1 rollback is local: on timeout or cancellation before retirement, reopen admission to the unchanged old transport; if retirement already succeeded, report the new generation's real availability and let ordinary reconnect policy act. Do not roll back dirty generations or replay an unknown remote mutation. A test showing an active lease closed by planned recycle, a lost DIRTY row, an unbounded blocked request, stale CLEAN after an overlapping write, or missed watcher invalidation stops the phase. A live daemon or mount failure exits this proposal's authority; it requires a separately approved operational response.

## Primary external references and limits

- [Linux kernel FUSE overview](https://www.kernel.org/doc/html/latest/filesystems/fuse/fuse.html): connection lifetime, `/dev/fuse` fd, request/abort behavior. Its statement about daemon death supports the conservative no-handoff conclusion; it does not prove that every conceivable custom handoff is impossible.
- [fusepy 3.0.1 source](https://sources.debian.org/src/python-fusepy/3.0.1-5/fuse.py/): `FUSE.__init__` calls `fuse_main_real`; `open/read/write/release` use high-level `fh` callbacks. This is the version pinned for Bazel/pip, as packaged by Debian; no live handoff interface is visible in that binding. The Nix-packaged CLI's version remains to be verified before implementation.
- [libfuse API documentation](https://libfuse.github.io/doxygen/fuse__lowlevel_8h.html): low-level session APIs are a different integration surface. Their existence is not evidence that this fusepy 3.0.1/high-level mount can transfer a live session safely.
