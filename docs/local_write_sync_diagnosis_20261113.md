# Local write to rsync member: bounded diagnosis

State: direct local-rsync skip and integrated false-CLEAN path reproduced synthetically; upload selection now forces transfer and the draft mount startup validator rejects observed suppressing options. Source base `66c640aec005feccd0bd585f3355295c3bb772ba`; no live cache, member, profile, mount, or log identifiers were inspected. The field cause remains unproven.

## Source trace and what is measured

1. A canonical `StorageFS.write` writes to the local cache and calls `CacheManager.mark_file_dirty` (`storage/fs.py`, `write`); `create`, `truncate`, and timestamp changes also record modifications. `CacheManager.mark_file_dirty` calls `StateManager.mark_dirty_from_cache_file`, which bumps `dirty_generation` and records DIRTY, size, and mtime in the index, then mirrors the row to the cache-file xattr (`storage/cache.py`, `mark_file_dirty`; `storage/state.py`, `mark_dirty`). Direct writes to the cache outside Storage do not take this supported path.
2. Canonical `release` flushes and queues DIRTY work (`storage/fs.py`, `_release`). `SyncExecutor._process_file_task` snapshots the generation, records SYNCING, hashes the cache file, checks for conflicts, calls the member's `copy_from_local`, calls `sync`, then reports the cache checksum to `member_written_cb` if the cache file identity stayed fixed (`storage/sync_executor.py`). An overlapping Storage write moves the generation and prevents the old attempt from publishing CLEAN.
3. `StorageFS._record_member_written` stats the member after the call and persists that member's basis with the checksum passed by the executor (`storage/fs.py`). **That checksum is inferred from successful upload and unchanged local identity; it is not a measured member hash.** A successful member call also records a location and may publish CLEAN. A transfer exception counts as a failed member and cannot make a sole-replica file CLEAN.
4. At source base `66c640a`, `RsyncBackend.copy_from_local` used `_run_rsync`, which constructed `rsync -a` without `--ignore-times` or `--checksum` unless caller options supplied one (`storage/backends/rsync.py`). The already-tracked quick-check hypothesis (`gh-112-rsync-quickcheck`) is that same-size, same-mtime destination bytes can be skipped while rsync exits successfully. The integrated synthetic regression below proves that route is reachable; it does not establish the field cause.
5. Reverification stats, hashes, and stats the member again against its persisted basis (`storage/fs.py`, `_reverify_member_copy`). `_settle_reverify` logs a mismatching measured digest and replaces the persisted member digest; it does not itself trigger resync. Both a genuinely rewritten member and a skipped upload followed by a false inferred baseline could lead to that log. The supplied INFO lines cannot distinguish them.

## Draft synthetic regression

`tests/test_rsync_backend.py` calls the production `copy_from_local` and real `_run_rsync` subprocess with two local files whose distinct bytes have identical size and nanosecond mtime. Only SSH metadata and remote-spec routing are replaced with local paths.

`tests/test_fs_revalidate.py` additionally drives `StorageFS.create`/`write`/`release`/`utimens`, the real `SyncExecutor` settlement and `StorageFS._record_member_written` callback, using local rsync for transfer. It covers changed-size success, equal-size/equal-mtime selection, an explicit legacy skip control that asserts CLEAN with stale member bytes and a local-assumed persisted hash, measured re-verification without a remote rewrite, a distinct genuine rewrite, and failure remaining non-CLEAN. The real conflict guard runs with a legitimate no-prior-location baseline; only backend selection and SFTP metadata transport are bounded by test doubles. Neither a FUSE mount nor SSH remote is exercised.

Invocation 2/7 ran the two focused targets with real rsync. The two `test_rsync_backend.py` cases failed behaviorally: `copy_from_local` returned, yet destination bytes remained `b"old bytes"` instead of `b"new bytes"`, both with default arguments and caller `--size-only`. The first integration run hit a fixture error (`PurePosixPath` has no `.exists()`) before transfer in four cases; its failure-settlement case passed. The fixture was corrected to wrap the path with `Path`. Invocation 3/7 stopped during dependency analysis before executing any test.

Root then authorized locked dependency resolution for the remaining invocations. Invocation 4/7, still on unchanged production `rsync.py`, gave the integrated behavioral RED: with equal-size/equal-mtime bytes, the real no-prior-baseline conflict guard allowed upload; rsync returned successfully, `SyncExecutor` published CLEAN, and the member still held old bytes. The direct rsync cases also failed on old bytes. The separate legacy-skip control passed, explicitly measuring persisted source hash against stale member hash and re-verifying without an intervening member rewrite. Ordinary changed-size upload and failure remaining non-CLEAN passed. The genuine-rewrite case failed at its added prerequisite assertion that upload bytes must first match, so it cannot misreport an already-skipped upload as a rewrite.

The focused production change passes `extra_args=["--ignore-times"]` to the upload call, after caller arguments in `_run_rsync`; it leaves read transfer, `-a`, and rsync's delta algorithm flags intact. Invocation 5/7 passed all five integration cases and the default direct upload case. The caller `rsync_args=["--size-only"]` direct case still failed on stale destination bytes: appending `--ignore-times` does not defeat `--size-only` in the actual subprocess. Ted subsequently ruled on startup validation; its implementation and evidence are in `docs/rsync_startup_validation_plan_20261113.md`. No field attribution follows from this synthetic evidence.
