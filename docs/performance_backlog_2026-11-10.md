## What is already built

- [#111](https://github.com/tedks/storage/issues/111) remains an open umbrella, but listing attributes, parallel member listing, and the listing lifetime work are closed in ditz. `NamespaceService.readdir` serves a fresh snapshot, schedules one background refresh for a stale one, and starts a foreground listing only on expiry ([`namespace.py:903-928`](../storage/namespace.py)); member calls run on per-member executors ([`namespace.py:1079-1112`](../storage/namespace.py)). The remaining `listing-foreground-single-flight` issue concerns **concurrent foreground** callers after expiry, not another general listing rewrite.
- [#112](https://github.com/tedks/storage/issues/112) remains an open umbrella, but `gh-112-skip-recorded` and `conflicts-off-browse-path` are closed. View checksums call `get_fast_checksum(..., allow_download=False)` on a worker ([`fs.py:1123-1161`](../storage/fs.py)). The old `field-listing-downloads-to-hash` report describes an earlier baseline, not evidence that current listing still downloads files. A separate open `gh-112-checksum-probe-gate` names a remaining connection-probe problem; do not re-add the removed fallback.
- [#29](https://github.com/tedks/storage/issues/29) and its old ditz prose predate the pooled SSH transport. `MemberConnection.acquire_sftp` now leases pooled channels and reserves capacity for non-bulk requests ([`ssh_pool.py:777-835`](../storage/backends/ssh_pool.py)). Investigate current channel occupancy and classification, not a new per-thread connection model.
- Streaming already avoids a whole-file speculative fetch for a sniff and bounds read-ahead while readers have not consumed enough ([`streaming.py:20-30`](../storage/streaming.py), [`streaming.py:734-757`](../storage/streaming.py)). After `readers_consumed`, the worker sweeps the file ([`streaming.py:705-732`](../storage/streaming.py), [`streaming.py:1253-1303`](../storage/streaming.py)). [#23](https://github.com/tedks/storage/issues/23) still has no shared range or byte budget and reports fetch counts/bytes rather than queue or foreground wait time ([`streaming.py:209-217`](../storage/streaming.py), [`streaming.py:496-509`](../storage/streaming.py)).

### 1. Reject or complete a promoted streaming prefix before write-open

**Tracker:** `streaming-prefix-write-open` (unstarted). **Intent:** a landed write must be visibly dirty and syncable. **Effort/risk:** small to medium / high correctness risk. **Can start without product ruling:** yes, if offline prefix reads remain available and write-open never edits an unindexed prefix.

**Evidence at pinned source:** a failed stream can install a prefix only when no index row exists ([`streaming.py:1037-1079`](../storage/streaming.py)); `open` treats any cached file as a cache hit, then the full-fetch fallback also returns on that cache hit ([`fs.py:2284-2320`](../storage/fs.py), [`fs.py:1890-1897`](../storage/fs.py)). `mark_file_dirty` returns `None` when there is no row ([`cache.py:411-434`](../storage/cache.py)); release queues sync only for an existing DIRTY row ([`fs.py:2544-2546`](../storage/fs.py)). The silent-write consequence is a static path inference and an existing tracker report, not a new reproduction.

**Owned seam:** `storage/fs.py` open/prefix handling and `storage/streaming.py` prefix contract, with `tests/test_fs_streaming.py`; avoid changing sync policy. **Acceptance:** a synthetic failed stream promotes a prefix; an `O_RDWR` or `O_WRONLY` open when the member is reachable either completes the file before editing or fails without editing; when the member is unavailable it fails safely or follows an explicitly ruled offline-write behavior. A successful write has a row, bumps generation, and reaches the normal sync queue; the full member tail is never replaced by a prefix. Preserve existing offline read of the prefix. Test open, write, close and index/member outcomes, including a concurrent prefix promotion. **Stop/escalate:** if preserving offline writes would require a new partial-file metadata contract, ask the product owner before defining it. Existing FUSE and remote gates remain mandatory for the implementation.

### 2. Make rsync upload ignore a stale size/mtime quick check

**Tracker:** `gh-112-rsync-quickcheck` (unstarted). **Intent:** sync success must mean the member has the bytes the mount marked dirty. **Effort/risk:** small / medium, with extra transfer cost. **Can start without product ruling:** yes for a targeted `--ignore-times` upload, while recording its wire-cost tradeoff.

**Evidence:** the upload calls `_run_rsync` without an upload-specific override ([`rsync.py:214-229`](../storage/backends/rsync.py)); that command starts with `rsync -a` ([`rsync.py:145-165`](../storage/backends/rsync.py)). The worker records upload success and location after the call ([`sync_executor.py:173-210`](../storage/sync_executor.py)). The issue reports same-size, same-mtime changed bytes can be skipped by rsync; this needs a synthetic remote reproduction before claiming it is fixed.

**Owned seam:** `storage/backends/rsync.py`, `tests/test_rsync_backend.py`, and `tests/test_remote_system.py`. **Acceptance:** an already-present member file and a changed local file with identical size and mtime are used in a Docker sshd/rsync test; after sync the member bytes match the local bytes, and the unchanged-file case retains correct behavior. Check option order when user `rsync_args` are present and preserve partial-dir semantics. **Stop/escalate:** if per-upload forced transfer violates an established user bandwidth contract, surface that cost before widening options. The remote gate is essential evidence.

### 3. Pipeline sequential SFTP range reads without weakening short reads

**Tracker:** `field-seq-read-serialized` (unstarted); related [#23](https://github.com/tedks/storage/issues/23). **Intent:** large files stream while first-byte and small sniff costs remain bounded. **Effort/risk:** medium to large / high protocol and cancellation risk. **Can start without product ruling:** yes for a bounded, feature-compatible range-read primitive; no field speedup should be promised.

**Evidence:** `SSHBackend.read_file` leases a channel, opens a remote file, seeks, reads and closes for each call ([`ssh.py:345-355`](../storage/backends/ssh.py)); the stream calls that primitive for each missing range ([`streaming.py:622-673`](../storage/streaming.py)). The tracker records a historical 2026-10-30 LAN observation at old `39e4b79`: 4–8 MiB/s sequential through the mount versus about 94 MB/s for pipelined `sftp.get` on the same transport. These numbers are diagnostic context, not a measurement of `a7467c6` or an expected gain.

**Owned seam:** SSH range API and streaming caller, with `tests/test_remote_system.py` and `tests/test_fs_streaming.py`; publish a narrow backend capability so local members and error fallback remain defined. **Acceptance:** Docker-backed test exercises a multi-chunk sequential read and a short sniff, counts bounded outstanding requests and bytes, compares returned bytes exactly, and covers seek, cancellation, timeout, disconnect/reconnect and reduced `MaxSessions`. A synthetic benchmark compares serial and proposed paths on the same container/network and reports distribution and configuration, without a fixed throughput threshold in the correctness gate. **Stop/escalate:** do not start unbounded SFTP prefetch or share a single `SFTPFile` concurrently without a proved ownership/cancellation contract. Coordinate with package 4 on channel leases.

### 4. Preserve a metadata channel under concurrent cold opens

**Tracker:** `threading-cold-open-pool-share` (unstarted); `listing-foreground-single-flight` is a separate follow-up. **Intent:** cold reads must not make namespace browsing appear hung. **Effort/risk:** medium / medium concurrency risk. **Can start without product ruling:** yes if a full-file fetch is classified as bulk while the actual short foreground range remains interactive.

**Evidence:** FUSE calls run under `interactive_request` ([`fs.py:129`](../storage/fs.py)); `MemberConnection` exempts interactive leases from its bulk limit ([`ssh_pool.py:762-768`](../storage/backends/ssh_pool.py), [`ssh_pool.py:796-835`](../storage/backends/ssh_pool.py)). A non-streaming cold open downloads the file before returning ([`fs.py:2317-2320`](../storage/fs.py), [`fs.py:1923-1942`](../storage/fs.py)). The tracker warns that several such opens can occupy every channel. This is a static contention path; its latency impact on current head needs a synthetic concurrent test. CPU load alone cannot diagnose a channel waiter or blocked network I/O.

**Owned seam:** request classification at `storage/fs.py`/backend call boundary and `storage/backends/ssh_pool.py` diagnostics, with `tests/test_remote_system.py` or an existing pool test. **Acceptance:** block several full fetches with a deterministic fake or Docker member, then show a listing/stat obtains the reserved lease within its defined deadline; verify the full fetches finish and no reserved channel is stolen after a caller gives up. Capture per-class lease wait, active/queued channel count and member identity before broadening scheduler policy. Keep streaming foreground range reads responsive. **Stop/escalate:** if the server caps channels to one, the existing pool cannot guarantee a reserve; report that condition distinctly. Avoid a global CPU-based worker policy.

### 5. Remove full remote downloads from pre-sync conflict checks

**Tracker:** [#74](https://github.com/tedks/storage/issues/74), `gh-74-fast-checksum`, `gh-74-no-hash-policy` (unstarted); related `gh-91-tmpfile-leak`. The product decision is filed as `oq-conflict-no-remote-hash`. **Intent:** conflicts stay visible and sync does not consume whole-file download bandwidth just to compare remote content. **Effort/risk:** medium / high conflict-safety risk. **Product ruling:** the no-remote-hash behavior must be decided before the implementation is accepted.

**Evidence:** each target goes through `check_conflict` before upload ([`sync_executor.py:173-190`](../storage/sync_executor.py)); it downloads the entire member file to a temp path and hashes it ([`conflicts.py:79-105`](../storage/conflicts.py)). The browse path already has a no-download checksum API ([`fs.py:1153-1160`](../storage/fs.py)), and SSH `get_fast_checksum` accepts `allow_download=False` ([`ssh.py:725-758`](../storage/backends/ssh.py)). The current exception path assumes no conflict ([`conflicts.py:101-106`](../storage/conflicts.py)); removing its download fallback without a failure policy could silently overwrite a changed member.

**Owned seam:** `storage/conflicts.py`, `storage/sync_executor.py`, `tests/test_sync_executor.py`, and `tests/test_remote_system.py`. **Acceptance:** a member with `xxh128sum` uses a remote digest and transfers zero member file bytes for the check; changed member bytes still yield CONFLICT; a member without a hash command, a timeout and an unreachable member follow the ruled policy and never silently publish a false CLEAN. Include temp-file cleanup on every failure path. **Stop/escalate:** choose with the product owner between blocking sync with an explicit unverified/error state and a bounded download fallback; neither may be guessed by the implementation lane. Validate checksum equivalence, including links, before replacing the method.
