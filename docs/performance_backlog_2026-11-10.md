### 1. Reject or complete a promoted streaming prefix before write-open

**Tracker:** `streaming-prefix-write-open` (unstarted). **Intent:** a landed write must be visibly dirty and syncable. **Effort/risk:** small to medium / high correctness risk. **Can start without product ruling:** yes, if offline prefix reads remain available and write-open never edits an unindexed prefix.

**Evidence at pinned source:** a failed stream can install a prefix only when no index row exists ([`streaming.py:1037-1079`](../storage/streaming.py)); `open` treats any cached file as a cache hit, then the full-fetch fallback also returns on that cache hit ([`fs.py:2284-2320`](../storage/fs.py), [`fs.py:1890-1897`](../storage/fs.py)). `mark_file_dirty` returns `None` when there is no row ([`cache.py:411-434`](../storage/cache.py)); release queues sync only for an existing DIRTY row ([`fs.py:2544-2546`](../storage/fs.py)). The silent-write consequence is a static path inference and an existing tracker report, not a new reproduction.

**Owned seam:** `storage/fs.py` open/prefix handling and `storage/streaming.py` prefix contract, with `tests/test_fs_streaming.py`; avoid changing sync policy. **Acceptance:** a synthetic failed stream promotes a prefix; an `O_RDWR` or `O_WRONLY` open when the member is reachable either completes the file before editing or fails without editing; when the member is unavailable it fails safely or follows an explicitly ruled offline-write behavior. A successful write has a row, bumps generation, and reaches the normal sync queue; the full member tail is never replaced by a prefix. Preserve existing offline read of the prefix. Test open, write, close and index/member outcomes, including a concurrent prefix promotion. **Stop/escalate:** if preserving offline writes would require a new partial-file metadata contract, ask the product owner before defining it. Existing FUSE and remote gates remain mandatory for the implementation.

### 5. Check conflicts by remote hash first, then a bounded local hash fallback

**Tracker:** [#74](https://github.com/tedks/storage/issues/74), `gh-74-fast-checksum`, `gh-74-no-hash-policy` (unstarted); related `gh-91-tmpfile-leak` and `gh-112-remote-hash-outlives-timeout`. Ted closed and synced `oq-conflict-no-remote-hash` on 2026-11-10 with a **policy ruling**: when remote hashing is unavailable, a bounded download and local hash is allowed. On 2026-11-17 he closed `oq-conflict-fallback-limits`, adopting the initial limits below with no user override. Neither ruling implements #74. **Intent:** conflicts stay visible, background checks do not consume unbounded member bandwidth, and foreground reads and browsing retain capacity. **Effort/risk:** medium / high conflict-safety risk.

**Evidence:** each target goes through `check_conflict` before upload ([`sync_executor.py:173-190`](../storage/sync_executor.py)); the current check downloads the entire member file to a temp path and hashes it ([`conflicts.py:79-105`](../storage/conflicts.py)). The browse path already calls `get_fast_checksum(..., allow_download=False)` ([`fs.py:1153-1160`](../storage/fs.py)). SSH's default `allow_download=True` silently selects its existing unbounded fallback ([`ssh.py:725-785`](../storage/backends/ssh.py)); `copy_to_local` uses `sftp.get` without a byte or whole-operation deadline ([`ssh.py:528-537`](../storage/backends/ssh.py)). The current exception path assumes no conflict ([`conflicts.py:101-106`](../storage/conflicts.py)). A per-member failure caught by the worker can still be followed by an aggregate CLEAN if other selected members satisfy the replica count ([`sync_executor.py:214-236`](../storage/sync_executor.py)); the new contract must distinguish unverified from a verified match.

**Ruled limits (Ted, 2026-11-17, `oq-conflict-fallback-limits`):** at most **64 MiB of actual bytes per member file**; **60 seconds total**, including wait, transfer and hash; **one active fallback per mount and per member**; at most **one second** waiting for the fallback slot; and reads of at most **1 MiB**. There is **no user override**. Unknown or oversize input, growth beyond the byte budget, timeout, cancellation and failed verification all leave the member unverified, with its upload blocked. Ted accepted, by adopting option A, that this stops fallback checks of multi-gigabyte files on members without a remote hash command: such a member stays unverified until it provides a remote digest or the limits change. These values are a conservative design choice, not the result of a measurement; no benchmark backs them.

**Proposed enforcement (this package's design; needs acceptance at decomposition):**

- The 60 seconds run from the fallback request through the final verified or unverified decision, so they include the post-transfer re-stat.
- Admit a file only after a member stat reports a size at or below 64 MiB; an unknown or larger size is unverified without downloading. Count actual bytes as well, because the file may grow after the stat. (The adopted `oq` text already gates on member stat and observed growth; this bullet adds only the ordering.)
- The one-second slot wait counts toward the 60 seconds (ruled: "including wait"; restated here for completeness).
- Check the deadline, the byte count and cancellation between reads.
- Cap the per-operation timeout by the remaining deadline. On expiry, close or cancel the active channel rather than wait on an unbounded `sftp.get`.
- Treat the transfer as background/bulk work; it never holds the SSH pool's foreground reserve.
- Bound the SSH channel wait by the remaining deadline as well. Since #175, bulk SFTP capacity waits have no deadline by default (see [Changes since the pinned audit](#changes-since-the-pinned-audit)).
- The path-level status that follows an unverified member is the item 4 proposal.

**Owned seam:** `storage/conflicts.py`, a narrow bounded-read/checksum backend contract in `storage/backends/base.py` and its SSH/rsync adapters, `storage/sync_executor.py`, and existing `tests/test_sync_executor.py`/`tests/test_remote_system.py`. This is a proposed interface, not implementation authority. **Acceptance:**

1. Attempt a remote digest once with `allow_download=False`; a valid remote digest transfers zero member file bytes for the check. A missing or unsupported remote hash command, which is how this package reads the phrase "remote hashing is unavailable" in Ted's policy ruling, may enter the bounded fallback. Malformed remote output (not a well-formed digest) is unverified and does not enter the fallback; treating it as unavailable would need a ruling. This is distinct from a well-formed digest that differs from the record, which is CONFLICT (item 4). The current signal cannot make these distinctions. Under `allow_download=False`, `SSHBackend.get_fast_checksum` raises connection errors as they are, but otherwise reports a missing command, any other non-zero exit (a missing file or permission denied, with stderr discarded), malformed or empty output and a `CommandTimeout` as one `ChecksumUnavailable` ([`ssh.py:750-779`](../storage/backends/ssh.py) at `0953369`). The proposed backend contract must report "hash command unavailable" (for example exit status 127 or a capability probe) separately from those other outcomes. Until it does, only a positively identified missing command may enter the fallback; never map `ChecksumUnavailable` to the fallback as a whole. A connection failure stays unverified. A remote-hash timeout is unverified and does not enter the fallback, under the current signal and by default. The `oq-conflict-no-remote-hash` question asked about remote hashing that is "unavailable or times out", but Ted's ruling names only unavailability. Whether a future contract may start the fallback after a timeout is a separate proposal that needs a ruling. If one is granted, it should apply only once the timed-out command's channel is positively canceled and closed, so that a still-running hash cannot compete with its own fallback. Cover the existing `gh-112-remote-hash-outlives-timeout` interaction without claiming that issue is fixed by a local timeout alone.
2. The bounded fallback hashes downloaded bytes locally with the same algorithm as the recorded checksum. Keep the live byte counter and monotonic deadline over admission, transfer, hash and the post-transfer re-stat. Verify the transfer covered exactly the statted size and re-stat afterward; an observed size/mtime change, short read, oversize, timeout, cancellation, local hash error, temp allocation/write error or failed cleanup is unverified. A stable pre/post stat cannot rule out same-size writes within a timestamp tick; that separate limit remains tracked by `oq-checksum-same-second-rewrite`.
3. Cancel and close the owned transfer on every exit. If staging is needed, use one exact owned temporary path and unlink it in `finally`, including exceptions and cancellation; never clean a shared temp glob. No partial file is accepted as a digest. A failing member must not leave a channel, worker or temp file behind.
4. A digest differing from the recorded member checksum remains CONFLICT, with no upload. A verified equal digest permits the existing upload path. An unverified outcome must not be encoded as `None`/“no conflict”: do not upload to that member, count it successful or write its location. The member-level outcome above (unverified, upload blocked) is what Ted ruled. The `oq-conflict-fallback-limits` text he adopted also says such files "remain DIRTY/ERROR", but the exact retry and aggregate rule is this package's **proposal** and needs acceptance at decomposition: keep the path DIRTY for retry or visibly ERROR after retry exhaustion, and do not publish CLEAN while a selected recorded member remains unverified, even if another selected member succeeds. Test that aggregate case explicitly.
5. Synthetic Docker and deterministic fake-member tests cover remote-digest success, missing utility, malformed remote output, timeout/cancel, stat race, each bound, local hash failure, cleanup and two-member partial success. While one fallback is blocked on a member whose pool can reserve a channel, a foreground stat/listing and short read should still obtain that reserved channel within its defined deadline. The final implementation runs all local gates, including the remote gate, on its exact head; this audit activates none.

**Stop/escalate:** the limits are fixed by `oq-conflict-fallback-limits`. The ruling forbids a user override. This package proposes that named module-level constants hold the only production values, and that tests may pass smaller bounds through an internal parameter that no profile option, environment variable or CLI flag can reach. Do not add a user override, and do not change a production value, without a new ruling from Ted; open a new `oq-` issue for that, informed by synthetic measurements. If the existing backend API cannot enforce a real deadline or cancellation, return an explicit unverified outcome and stop rather than calling its unbounded copy. A change to absent-baseline behavior remains outside this package and belongs to #91's separate decision.
